# 식자재 발주 도우미 (해커톤 주제 1)

매장의 판매 추세·재고·사용기한·공급사 발주 조건을 함께 따져 **오늘 무엇을 얼마나 발주해야 하는지** 추천하고, 그 이유를 보여주는 웹 서비스입니다.

- **배포 주소**: https://hackathon-team6.vercel.app
- **테스트 계정** — 역할마다 필요한 화면이 따로 열립니다. 로그인 화면의 '심사용 테스트 계정'을 누르면 자동 입력. **휴대폰으로 보는 것을 기준으로 만들었습니다.**

  | 역할 | 매장 | 아이디 | 비밀번호 | 첫 화면 |
  |---|---|---|---|---|
  | 직원 (매장 공용) | 가상매장 A~C | `s01-staff` ~ `s03-staff` | `staff01!` ~ `staff03!` | 오늘 점검 |
  | 점장 | 가상매장 A~C | `s01` ~ `s03` | `cheese01!` ~ `cheese03!` | 오늘 주문 |
  | 슈퍼바이저 | 전 매장 | `sv` | `super01!` | 매장 진단 |
- 과제·데이터 명세: `식자재_관리_및_발주_자동화_요구사항과_데이터명세서.md`
- ⚠ 제공 CSV는 저장소에 올리지 않습니다 — `data/raw/`, `*.csv`, 생성 JSON, `.env*`, `.vercel` 은 `.gitignore` 처리

## 화면 설계 원칙 — "기술 설명보다, 실제 사용자가 간단하게 쓸 수 있는가"

이 서비스를 매일 여는 사람은 데이터 분석가가 아니라 **점장, 또는 점장 대신 로그인한 아르바이트생**입니다. 영업 준비로 바쁜 아침에 화면을 깊게 읽지 않습니다. 그래서 대시보드와 화면 구성의 기준을 "계산이 얼마나 정교한가를 보여주는가"가 아니라 **"사용자가 30초 안에 오늘 할 일을 끝낼 수 있는가"**로 잡았습니다.

**누가, 얼마나 자주, 무엇을 하려고 들어오나**

| 사용자 | 빈도 | 하고 싶은 것 | 화면에서의 위치 |
|---|---|---|---|
| 점장·알바 | 매일 아침 | 오늘 뭘 몇 개 주문해야 하나 → 주문 끝내기 | 첫 화면 맨 위 |
| 점장·알바 | 매일·가끔 | 냉장고 세어 본 수량 넣기, 급한 일(품절·기한 임박) 확인 | 첫 화면·바로 가기 |
| 점장 | 가끔 | 공급사 조건·단가 수정, 판매 기록 올리기 | 별도 메뉴 |
| 본사·심사자 | 드물게 | 예측 근거, 계산 설정, 데이터 분석·검증 결과 | 뒤쪽 메뉴(필요할 때만) |

**원칙**
1. **결론 먼저, 근거는 눌렀을 때** — "소고기 패티 3박스"를 먼저 보여주고, 왜 3박스인지는 품목을 눌러야 펼쳐집니다. 계산식·통계 용어(안전재고, z, 표준편차, 기준일)는 첫 화면에 쓰지 않습니다.
2. **사람이 세는 단위로** — g·ml 대신 박스·팩, 숫자 대신 "며칠 버틸 수 있는지". 빨간색은 정말 급할 때(다음 입고 전에 떨어짐)에만 씁니다.
3. **할 일 순서대로** — 대시보드는 숫자 카드가 아니라 "오늘 할 일"을 급한 순서로 보여주고, 각 할 일에 마감까지 남은 시간과 바로 가는 버튼을 붙였습니다.
4. **문장은 행동으로 끝나게** — "최소 발주금액 미달" 대신 "2만원 모자라 이대로는 주문이 안 돼요 → 감자 1박스 더 담기".
5. **로그인하면 끝** — 계정마다 소속 매장이 정해져 있어 매장을 고를 필요가 없고, 내 매장 데이터만 보입니다.
6. **고급 기능은 숨기되 없애지 않음** — 수요 증감·여유분 수준 같은 설정과 분석 결과는 '추천 설정', '가정·근거' 메뉴로 분리해 필요한 사람만 들어가게 했습니다.

**이 원칙으로 바꾼 것 (반영 완료)**

| 바꾸기 전 | 바꾼 뒤 |
|---|---|
| 숫자 카드 4개(부족 예상·오늘 발주·임박·과잉) | '오늘 할 일' 번호 목록 + 마감까지 남은 시간 + 바로 가기 버튼 |
| 남은 양 95,410g | 8박스 (95.4kg) · 1.7일치 |
| 차트 "실제기말 / 예상기말" | "남은 양(실제) / 남은 양(예상)", 오늘·다음 입고 표시 |
| 모든 품목 빨간 "1일치 미만" | 오늘 아침 입고분 포함, 빨강은 다음 입고 전에 떨어질 때만 |
| 계산 근거: 수식 나열 | "왜 3박스인가요?" — 언제 도착하고, 며칠 버텨야 하고, 그동안 얼마 쓰는지 문장으로 |
| 화면 옆에 슬라이더 7개 | 매일 바꾸는 값만 남기고 나머지는 '추천 설정'으로, 항목마다 쉬운 설명과 바꾸면 얼마나 달라지는지 |
| "계산 기준 조정" | "추천 방식 바꾸기" / "얼마나 넉넉하게 주문할까요? 넉넉하게·보통·타이트하게" |
| 최소 발주금액 미달 경고만 | 미루기 또는 "제안대로 담기" 버튼 하나로 해결 |

**2차 단순화 (반영 완료)**

| 바꾸기 전 | 바꾼 뒤 |
|---|---|
| 메뉴 6개 + 왼쪽에 기준일·시각 입력 | **오늘 주문 / 재고 세기 / 더보기** 3개. 상세 화면 6개와 시연용 날짜·시각은 '더보기' 안으로 |
| 발주서 = 표 7열 + 숫자 입력칸 | 공급사별 **체크리스트 카드**: 품목마다 큰 수량 [−][+], 이유 한 줄("도착 후 1일 버틸 양 · 하루 약 523개"), 자세한 근거는 '왜?'를 눌렀을 때만 |
| 전체 '발주 확정' 버튼 하나 | 공급사별 **"공급업체 B 주문 완료"** → 카드가 "✓ 주문 완료"로 접히고 "2곳 중 1곳 완료" 진행 표시, 메뉴에 남은 주문 수 배지. 새로고침해도 유지 |
| 실사 = 22개 품목 표에 g 단위 입력 | **재고 세기**: 한 품목씩 넘기며 사람이 세는 단위(박스·개)로 입력, 반 박스는 0.5. 바뀐 것만 세고 중간에 저장 가능, 장부와 30% 넘게 다른 품목만 다시 확인 |
| 처음 방문 안내 박스 | 없앰 — 화면 자체가 할 일 순서 |

- 공급사별로 따로 주문을 완료할 수 있도록, 확정 발주를 '기준일 × 공급사'별 마지막 것으로 입고 예정에 반영하게 계산 규칙도 바꿈(테스트 추가)
- 이후: 휴대폰 화면 대응(아래쪽 탭바, 큰 버튼) → 아래 3차에서 반영

## 3차 — 역할별 화면 · 공유 점검표 · 매장 진단 · 모바일 (현장 인터뷰 반영)

"이 앱이 한 가지 일만 확실히 줄여준다면?"에 대한 현장 답:
1. **현장 직원** — 수기 체크리스트 때문에 생기는 **중복 점검**(한 명이 냉장고 온도를 쟀는데 다른 직원이 몰라서 또 잼)
2. **슈퍼바이저** — 매장 방문 전 **손익 파악·문제 진단**에 드는 시간

그래서 로그인을 역할별로 나누고, 역할마다 첫 화면을 그 사람의 일 하나에 맞췄습니다. 휴대폰으로 볼 일이 더 많다고 해서 **모바일 우선**(화면 아래 탭바, 큰 버튼, 숫자 키패드)으로 바꿨습니다.

| 역할 | 첫 화면 | 할 수 있는 것 | 막힌 것 |
|---|---|---|---|
| 직원 (매장 공용 계정 + 이름 한 번 입력) | 오늘 점검 | 점검 기록·되돌리기(본인 것), 재고 세기 | 발주·기준정보 수정 |
| 점장 | 오늘 주문 (+ 맨 위 "오늘 점검 n/8 완료") | 기존 기능 전부, 점검 항목 추가·끄기 | 매장 진단 |
| 슈퍼바이저 | 매장 진단 | 전 매장 비교, 매장별 상세 열람(매장 선택) | 모든 쓰기 |

**공유 점검표 (중복 점검 없애기)**
- 오픈 전 / 점심 후 / 마감으로 묶은 8개 기본 항목(입고 검수, 냉장 0~5℃·냉동 −18℃ 이하 온도, 사용기한 임박 품목 — 엔진이 계산한 임박 품목 자동 표시, 재고 세기, 마감 폐기). 점장이 항목 추가·끄기
- 끝난 항목은 **누가·몇 시에** 했는지 바로 보임 → 다른 직원은 다시 안 함
- 같은 날 같은 항목은 DB 유일 인덱스로 **한 번만** 저장. 두 명이 거의 동시에 눌러도 늦은 쪽엔 "이미 ○○님이 07:15에 기록했어요"
- 업무 중 폰을 계속 볼 수 없는 환경이라 실시간 연결 대신 **열 때 · 화면으로 돌아올 때 · 20초마다** 새로고침
- 온도가 기준을 벗어나면 빨간 표시 + "점장님께 알려 주세요"
- 테이블: `app_check_items`, `app_check_logs` (Drizzle)

**슈퍼바이저 매장 진단 (방문 전 손익 파악)**
- 최근 2/4/8주 vs 직전 같은 기간, 매장별 카드(문제 있는 매장이 위로)
- 지표(모두 제공 데이터): 매출, **식자재비 = 실제 소진량 × 단가**(팀 분석 `ana_ingredient_daily.consumed_cost`), 식자재비율, 폐기율(기한 경과 비중), 품절 수량·못 판 금액(× 판매가), 긴급발주 횟수·금액, 주별 식자재비율 추이, 오늘 점검 진행
- **경고 기준(화면에 문장으로 표시)**: 식자재비율이 다른 매장 평균·직전 기간보다 0.5%p 이상 높음 / 폐기율 1.5배 이상 / 긴급발주·품절 1건 이상
- 경고가 있으면 폐기 상위 품목·사유로 **준비할 해결책**을 자동 제시(예: 기한 경과 → 발주량·포장 단위 조정, 보관 불량 → 온도 기록 확인)
- **인건비는 제공 데이터에 없어 제외**
- 현재 데이터(9/3~9/30) 결과: 가상매장 A — 폐기율이 다른 매장 평균의 2.1배, 긴급발주 1회(우유), 품절 8개. B·C는 평소 수준. 식자재비율은 세 매장 모두 35.1~35.4%로 고름

## 4차 — 공휴일 캘린더 연동 · 손익 관리 기준 · 매장 간 이동 (2차 인터뷰 반영)

**공휴일 캘린더 연동**
- 데이터 이후(10/1~) 공휴일을 **대한민국 공휴일 캘린더(구글 공개 iCal)** 에서 하루 한 번 받아옴. '공휴일'만 쓰고 기념일(국군의날 등)은 제외. 연결 실패 시 미리 넣은 가정값(10/3·10/5·10/9)
- 오늘 주문 화면에 **2주 안의 공휴일**과 이 매장의 지난 공휴일 판매 배수를 보여 주고, 날마다 **지난 공휴일처럼(배수 적용) / 평일처럼 / 쉬는 날(판매 0)** 을 고르면 주문 수량이 바로 다시 계산됨
- 예: 가상매장 A(오피스 상권)는 지난 공휴일에 평소보다 33% 덜 팔림(×0.67) → 개천절·한글날 전후 주문이 자동으로 줄어듦

**손익 관리 기준 (슈퍼바이저)**
- 현장 기준: **식자재비율 매출의 30%, 인건비율 20%**. 매장 진단의 1차 경고 기준을 '식자재비율 30% 초과'로 바꾸고, 다른 매장 평균·직전 기간 비교는 함께 표시(기준 이내여도 상대적으로 0.5%p 이상 높으면 경고)
- 식자재비 비중 상위 3품목과 단가 변화를 원인 후보로 제시 → 정량·원가 높은 메뉴 비중 확인
- 인건비율은 기준(20%)만 표시 — 인건비 데이터가 없어 계산하지 않음
- 현재 데이터: 세 매장 모두 식자재비율 35.1~35.4%로 **기준보다 5%p 이상 높음**. 비중 상위는 소고기 패티·슬라이스 치즈·냉동 감자(약 45%), 이 기간 단가 변화는 없음

**매장 간 이동 (본사 승인 없이 매장끼리 협의, 배달대행 운송·예치금 사용)**
- 오늘 주문의 '다음 입고 전에 떨어지는 품목'마다 **여유 있는 다른 매장**을 표시(그 매장도 3일치는 남기는 양만 셈, 제공 재고 마지막 날 마감 기준) → 긴급발주 전에 옮겨오기 먼저 검토
- 슈퍼바이저 진단에 '다른 매장에서 빌려 온 횟수'(`transfers.csv`) 표시 — 잦으면 상시 부족 품목 신호
- 요청·승인·기록 절차는 현장에서도 아직 정해지지 않아(추가 확인 필요) 이동 기록 기능은 만들지 않음

**검증**: 규칙 단위 테스트(`diagnosis.test.ts`, `holidays.test.ts` — iCal 파싱, 공휴일 운영 방식 3가지) 46개 통과 · 로컬 실제 요청으로 캘린더 연동(10/1 이후 공휴일 출처 '캘린더'), 진단 기준, 이동 후보(점장 200 / 슈퍼바이저 403) 확인

**3차 검증**: 규칙 단위 테스트(`diagnosis.test.ts`) + 로컬 서버 실제 요청 30건(역할별 화면 이동·API 403, 두 직원 동시 기록 시 201/409, 슈퍼바이저 매장 선택) 모두 통과, 휴대폰 크기(390×844)로 세 역할 화면 확인

## 핵심 계산 규칙 (명세서 기준)

- 수요 예측(팀 발주 최적화 엔진): 판매 확정 기준 수요(`demand_qty − cancel_qty`)로 메뉴별 최근 4주 수준 × 매장 요일 지수 × 공휴일 배수(10/3·10/5·10/9 추가 가정). 미취급 기간은 제외
- 소요량 = 메뉴 예측 × BOM. 세트는 세트 자체 BOM(구성품 합산 안 함)
- 재고·소진은 사용단위, 발주는 포장 단위로 올림. 단가는 발주일 기준 `valid_from`
- 하루 순서: 07시 입고 → 영업 전 실사 → 발주 판단 → 판매 소진(사용기한 빠른 묶음부터) → 마감 후 기한 도래분 폐기
- **지금 남은 양** = 전날 마감 재고 + 오늘 07시 입고분 (발주 판단 시점)
- 발주량(팀 발주 최적화 엔진) = 이번 입고일 ~ 다음 발주 입고 전날까지 예상 부족분 + max(0, 안전재고 − 남을 양). 안전재고 = z × 하루 사용량 예측 오차(최근 56일) × √(책임 일수+1)
  - z: 넉넉 2.05 / 보통 1.28 / 타이트 0.67, 사용기한 14일 이상 품목 최소 2.05, 최근 28일 품절 품목 +0.36(최대 2.33)
  - 폐기 고려 감량: 품절이 안 늘고 마지막 1단위의 절반 이상이 버려질 전망이면 줄임 / 최소 발주금액 미달 시 미루기 또는 오래 가는 품목 보충안
  - 팀원 Python 엔진(`feature/order-optimization` `engine.py`)과 같은 데이터(S01, 10/1)로 비교해 22개 품목 추천 수량·안전재고가 모두 같음을 확인
- 공급사 발주 요일·마감(정각 불가)·리드타임·입고 요일, 품목 최소 발주수량, 발주서 최소 금액 반영
- 실사 입력: 감소분은 오래된 입고 묶음부터, 증가분은 가장 최근 묶음에 반영
- 판매 업로드: 제공 기간 이후 재고를 판매(확정 수량 × BOM)로 이어 계산 → "추정 재고"로 표시, 실사 입력 시 보정

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 1. 확인·검증 | 17개 파일 존재, 키·단위·재고 등식 등 점검 | `pipeline/reports/validation.md` |
| 2. 팀 전처리·EDA | 팀 저장소 `main`의 `pipeline.py`(팀원 작성)를 **그대로** 받아 실행. 검증 FAIL이면 여기서 중단 | `pipeline/reports/analysis/` |
| 3. 웹앱 집계 | 일별 수요·폐기 집계, DB 장애 시 쓸 JSON | `web/src/data/generated/` |
| 4. Neon 적재 | `raw_*`(원본) · `agg_*`(웹앱 집계) · `ana_*`(팀 분석 표) · `ana_meta`(EDA 요약·원본 해시·실행 기록) | Neon |

- **안전한 교체**: 모든 표를 `<이름>__new`에 먼저 넣고 한 트랜잭션 안에서 이름을 바꿔 교체합니다. 중간에 실패하면 기존 데이터가 그대로 남고, 운영 중인 앱은 반쯤 적재된 표를 보지 않습니다.
- **팀 코드는 복사·수정하지 않음**: 실행할 때마다 `--team-ref`(기본 `team/main`)에서 최신 `pipeline.py`를 꺼내 씁니다. 어떤 커밋으로 만들었는지 `ana_meta`의 `run_info`에 남습니다.
- 확인 결과: 같은 원본으로 실행한 결과가 팀 저장소에 올라온 `analysis/` 파일과 바이트 단위로 같습니다.

| 옵션 | 용도 |
|---|---|
| `--no-db` | 적재 없이 결과 파일만 만들어 확인 |
| `--skip-raw` | 원본·웹앱 집계는 그대로 두고 팀 분석 결과(`ana_*`)만 다시 적재 |
| `--raw <폴더>` | 다른 위치의 원본 사용 |
| `--team-ref <ref>` / `--team-script <경로>` | 다른 브랜치나 로컬 파일의 팀 코드 사용 |

원본(`raw_*`)을 다시 적재했다면 Vercel을 재배포해 서버의 기준 데이터 캐시를 비우세요.

## 로그인·권한

- 계정은 매장마다 관리자 1명(`s01`~`s03`, 위 표). 비밀번호는 코드에 **scrypt 해시로만** 저장 — DB 장애와 상관없이 로그인 가능
- 세션: 서명(HMAC-SHA256)한 HttpOnly 쿠키, 12시간. 서명 키는 `SESSION_SECRET`(없으면 `DATABASE_URL`에서 파생)
- `web/src/proxy.ts`가 로그인 전 화면은 로그인 페이지로, API는 401로 막고, **각 API에서도 세션을 다시 확인**해 매장을 로그인 매장으로 고정
  - 실사 입력·판매 업로드·발주안 저장은 로그인 매장 것만. 다른 매장 판매가 섞인 CSV는 거부
  - 기준정보(공급사 조건·포장 단위)와 단가는 매장 공통 조건이라 모든 매장 관리자가 함께 관리
- 같은 아이디로 5번 틀리면 5분간 로그인 제한, 틀린 아이디·비밀번호는 같은 문구로 안내(계정 존재 여부 노출 방지)
- 한계: 데모용 고정 계정이며 비밀번호 변경·계정 관리 화면은 없음
